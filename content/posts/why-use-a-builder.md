## 一句话说清这次改了什么

前两版网站，页面是**访客打开浏览器之后**才拼装出来的：

- 第一版：内容写死在 HTML 文件里，你怎么写浏览器就怎么显示。
- 第二版：HTML 只剩一个空壳，正文由 JavaScript 去读 JSON，再现场生成。

这一版不一样。我在本地敲了一句命令，Astro 就把所有页面**预先渲染成了完整的 HTML 文件**。访客拿到的，就是成品。

## 怎么自己验证这个差别

最直接的办法是看源代码。

打开浏览器，在页面上右键选择「查看网页源代码」——注意是「源代码」，不是「检查元素」。

- **第二版**：你会看到文章列表那个容器是空的，正文内容一个字都没有。因为它要等 JS 跑完才出现。
- **第三版**：文章标题、日期、正文、页眉页脚，全部都在源代码里，一个字不缺。

另一个更极端的验证方式是**禁用 JavaScript**（浏览器设置里可以关，或者用开发者工具的命令面板）。

- **第二版**：列表区域是空的，只剩一句「需要 JavaScript 才能显示」的提示。
- **第三版**：完全正常，一个字都不少。

## 这个差别有什么实际价值

三个层面，从易见到不易见：

**第一，搜索引擎。** 爬虫抓到的就是最终内容，不需要执行 JavaScript。对内容型站点，这是最实际的收益。

**第二，首屏速度。** 浏览器不必下载、解析、执行脚本，再等一次网络请求拿到数据。省掉的正好是最关键的那段时间。

**第三，也是最容易被忽略的——可靠性。** 页面内容不再依赖任何运行时的东西：不依赖 JS 执行成功，不依赖那个 JSON 文件还能被取到，不依赖网络在那一刻不出问题。构建成功，产物就是确定的。

> S2 的页面是「算出来的」，S3 的页面是「造出来的」。前者每次访问都要重算一遍，后者只造一次。

## 代价是什么

公平地说，构建不是免费的：

- 多了一层**构建步骤**。写完之后要跑 `npm run build`，不是双击文件就能看。
- 多了一个 **Node 环境和依赖目录**（`node_modules`，几百 MB）。
- 多了一套**需要理解的概念**：内容集合、布局、组件、构建产物。

这些成本换来的，是「新增一篇文章 = 新建一个 Markdown 文件」这套流程。

## 所以到底该怎么选

判断依据其实很朴素：

- 文章少于十篇、只想快速上线、不打算长期维护 → 手动写 HTML 完全够用，别引入构建工具。
- 打算长期写、要管理几十上百篇内容、需要统一的版式和一致的元信息 → 构建器的收益会迅速超过它的学习成本。

工具不是越新越好，是**匹配当前问题**才好。这一版之所以该用构建器，是因为它要解决的问题——版式重复、内容与结构混在一起、加文章要动多个文件——已经真实存在了。
